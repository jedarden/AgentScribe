# bf-5a20: aider_input.rs Wiring Validation

## Task Summary

Validate `src/parser/aider_input.rs` is wired end-to-end or cleanly removed.

## Findings

### 1. ✅ AiderInputHistory::load_from_file IS called in the actual scrape path

**Complete wiring path:**
```
Scraper::scrape_file() (src/scraper/mod.rs:445)
  ↓
  parser.parse(file_path, plugin) 
  ↓
  MarkdownParser::parse() (src/parser/markdown.rs:266-290)
  ↓
  Self::load_companion_input_history(source_path) (line 277)
  ↓
  AiderInputHistory::load_from_file(&companion) (line 84)
```

The flow is:
1. Scraper dispatches to `MarkdownParser` based on `LogFormat::Markdown`
2. `MarkdownParser::parse()` attempts to auto-discover a sibling `.aider.input.history` file
3. If found, it loads the history and uses it to enrich user event timestamps
4. The enrichment happens in `enrich_with_input_history()` (line 52-74)

### 3. ❌ AiderInputEntry is an orphaned export

**Export chain:**
- Defined in: `src/parser/aider_input.rs:20-26`
- Re-exported in: `src/parser/mod.rs:12` via `pub use aider_input::{AiderInputEntry, AiderInputHistory};`

**Usage analysis:**
```bash
$ grep -r "AiderInputEntry" --include="*.rs" | grep -v "test" | grep -v "mod tests"
src/parser/aider_input.rs:pub struct AiderInputEntry {
src/parser/mod.rs:pub use aider_input::{AiderInputEntry, AiderInputHistory};
```

`AiderInputEntry` is ONLY used:
- In its own definition
- In the re-export
- In tests within `aider_input.rs`

It is NEVER used in production code. The struct is defined for clarity (represents a single parsed entry), but the public API only exposes `AiderInputHistory` which internally uses a HashMap.

**Recommendation:** Remove `AiderInputEntry` from the public re-export in `src/parser/mod.rs`. Keep it in the module (it's used internally and in tests) but don't export it. This is cleanup, out of scope for this bead.
